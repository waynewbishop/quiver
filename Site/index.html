How it works

It’s just an Array.

Quiver adds numerical methods directly to Swift’s standard Array through extensions. A plain [Double] gains the math without becoming a different type, so it still flows straight into SwiftUI, Swift Charts and SwiftData.

The compiler knows what fits.

Swift’s type system validates math at compile time. Constrained extensions expose operations only on compatible types, while [Double] and [[Double]] define vectors and matrices as plain arrays, with dimensions checked when the code runs.

import Quiver let v = [3.0, 4.0] // Direction: a unit vector (length of 1) pointing the same way v.normalized // [0.6, 0.8] // See the rational form v.normalized.asFractions() // [3/5, 4/5]

Models

Models are always ready.

There is no empty or unfitted state. The fit method returns a trained model, so calling predict on something untrained cannot compile.

Trained on creation

fit is the only way in.

No runtime error for “model not fitted”. The situation cannot arise.

let model = KNearestNeighbors.fit(
    features: trainingData, labels: labels, k: 3)
let predictions = model.predict(newData)
Immutable

Learned parameters never drift.

Coefficients, centroids and learned parameters cannot change once the model exists. A whole category of accidental-retraining bugs disappears.

Codable

Train once, ship it.

Every stored property is a basic Swift type, so models encode to JSON with no extra code. Save one to disk and load it on the next launch without retraining.

Failure in the return type

The signature says how much care a fit needs.

try LinearRegression.fit(...)    // can fail
KNearestNeighbors.fit(...)       // cannot fail
[Double].polyfit(...)            // nil on failure

Models share their prediction interface through two protocols. Code written against Regressor accepts LinearRegression, Ridge and GradientDescent interchangeably, and code written against Classifier does the same for every classifier.

Concurrency

Train off the main thread.

Fitted models in Quiver are Sendable. A fitted model is an immutable value, so it crosses task boundaries with nothing to lock and nothing to coordinate.

@Observable @MainActor final class WorkoutAnalysisViewModel { var model: KMeans? // Fits off the main thread and stores the result for the view. func train(from sessions: [[Double]]) async { model = await Task.detached { KMeans.fit(data: sessions, k: 3, seed: 42) }.value } }

Long fits stay off the interface.

Run a fit on a detached task and await the trained model back. The interface keeps drawing while training runs.

Predict from many tasks at once.

Prediction is a pure read against immutable parameters, so any number of concurrent tasks can call predict without serialization.

Divide the work across cores.

Pairwise comparisons and other heavy operations split cleanly with withTaskGroup, and the results update SwiftUI when training completes.

    On the server, too.
    
      
    Quiver has zero dependencies, so the search code that runs on an iPhone runs inside a Vapor app unchanged. The [Double] Vapor decodes from JSON is the same [Double] Quiver computes on, with no subprocess and no second runtime.

    The logic for a Swift vector database
    This example ranks a small dictionary. For a catalog that grows, EmbeddingIndex stores each vector beside its label, ranks a query against all of them by cosine similarity, and saves as a Codable snapshot. Those are the core operations of a vector store, written in Swift.
    
      
    Swap the vectors, keep the ranking
    Here both tables are made by hand. A sentence model, plugged in through Quiver’s Embedder protocol, would produce the vectors instead, and the ranking with nearest(to:k:) stays the same.
    
      
    The retrieval half of RAG
    A /search route is retrieval. Feed its results to a language model as context and the server has a full RAG pipeline, with Quiver handling the search.
    
      
    Built on the CPU
    Quiver runs on the CPU with plain Swift arrays and no dependencies, so the same code runs unchanged on Apple Watch, iPhone and the Mac. Heavy work spreads across every core with Swift concurrency.

    Notebook › Examples › The Central Limit Theorem in Action
    
        
    See the theorem in action.
    
        
    Start with a skewed population, draw a thousand small samples from it, and bin their means. The underlying data is nowhere near normal, but the sample means assemble into a classic bell curve. With a fixed seed, every student in the room produces the exact same histogram on their first run.
    
        
    // Seeded so the histogram comes out identically on every run.
var rng = SeededRandomNumberGenerator(seed: 42)

// A skewed population: rate = 0.5, so the population mean is 2.0.
let population = [Double].randomExponential(
    10_000, rate: 0.5, using: &rng)

// Draw 1,000 samples of size 50 and record the mean of each.
let sampleMeans = population.samplingDistributionOfMean(
    sampleSize: 50, iterations: 1000, seed: 42)

for bin in sampleMeans.histogram(bins: 5) {
    print(bin.midpoint, bin.count)
}
